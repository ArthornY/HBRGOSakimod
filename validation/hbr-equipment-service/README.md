# 佐月商店交易验证

本项目加载每档不可变候选 DLL，执行生产 `ElectronicSoldierManual.ApplyEquipmentCommand`、原生 `PlayerCmd.LoseGold/GainGold`、真正的 `Player.GoldChanged` 回调及 Ritsu equipment managed action 的序列化/派发。报价与生成器读取实际同持有者永久卡组的佐月 policy，客户端命令不携带价格、优惠、候选装备或退款金额。

覆盖：

- 折扣相乘后仅一次向下取整，最低1金币；装备、材料和炼金共用每实际幕的首购，第三幕后不能因装备 tier 封顶而共用收据。首炼保证分别记录。
- 金币不足、扣金前取消、扣金后通知异常、退款到账后通知异常、Store 已写入后异常均不消耗 RNG/首购/首炼收据，恢复同持有者真实金币及 equipment 字符串和缓存。每持有者租约拒绝自己重入，另一持有者的正常交易不被阻挡或回滚。
- 原件先成交；重炼额外收费按原折扣实付款的一半，不扣除此前退款，最低1金币。不再使用首购/首炼或触发第二次退款。同交易至多重炼一次。
- 第二候选未进入背包，待选择时锁定所有装备/购买/出售/改造操作，奖励 Claim 仍可领取；关闭并重读保存 JSON 可继续选择。选择只替换原件 ID，双击或过期 revision/transactionId 不会再次收费或生成。
- 未付重炼前原件成功被装备、卸下、改造或出售时，关闭旧 offer；失败操作不关闭。后续购买不会删除已成交的原件。
- 实际生成器验证四种饰品首幕4→5、第二幕5→6、第三幕最高6封顶、已开+栏恰加1且封顶；护符首幕实际30%边界及高级保底。只有生成器阈值案例控制底层原始随机数，其余支付/退款/RNG账本案例使用真实保存的装备随机流。

## 原有商品缺档边界

已有5星项链、6星戒指原本只在掉落池。仅佐月启用且当前请求的 kind/rank 在炼金池缺档时，可选择同 kind/rank 的现有掉落模板，不改原模板或普通掉落。完全不存在的星级不虚构：原作项链没有2星，仍按原来的最近可用星级规则处理，测试同时验证普通方向选择1星、促星方向选择3星，并确认商品表未增加条目。护符仍只有普通/高级两档，最高保证为已有高级护符，不伪造5/6星护符。

## 事务和验证边界

回滚范围为此次交易所属玩家的金币和 equipment 保存/缓存；其他玩家成功交易不回滚。提交后的 DP 同步、Flash、预览通知属于后续刷新；本套件控制其视觉/场景叶子，没有模拟提交后刷新故障。原生金币钩子独立修改的其他系统状态也不在设备事务回滚范围。

没有启动 Godot、实际手册界面、真实网络传输、打包或上传。beta 编译使用原始依赖，运行仅在独立测试副本隔离已验证的 Sentry 初始化调用，报告附原始 SHA 和其余字节一致的证明。链接的旧 host 会产生既有 nullable 警告，与生产0警告构建分开记录。

运行示例：`powershell -File outputs/31c-mari55-20261115/run-suite.ps1 -Suite hbr-equipment-service -Profile stable -ReportName equipment-service-report.json`；beta 添加 `-CheckArgs --isolate-telemetry`。同项目的 stable/beta 必须顺序构建。报告在对应档位目录。
